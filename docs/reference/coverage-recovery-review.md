# Coverage recovery source review

Reviewed 2026-10-26. Public vendor documentation, local sanitized diagnostics, and bounded live GET smoke probes were used. Probe responses stayed in memory; only counts, fixed paths, types and fixed classifications were printed. No keys or raw responses were saved.

- The vendor [product-type operation](https://www.postman.com/servicedeskplus/servicedesk-plus-api/request/u4eoaf0/get-all-product-types) documents the `/asset_modules` GET. The supplied value-free response shape confirms an `asset_modules` array, while the earlier scanner expected `all_product_types`. Both explicit wrappers are accepted for this endpoint only; no generic wrapper inference is used.
- The [build 15100 Asset API changes](https://help.servicedeskplus.com/asset-api-changes) documents `/asset_computers` for computer detail and `/asset_workstations` in its workstation-list section. The document is not uniform in its naming. The implementation retains the current primary, adds only the documented workstation-list fallback after unsupported responses, then retains the legacy fallback. No detail route is added for the workstation-list fallback. Type-specific metadata follows the same source's product-layout guidance.
- The [Change metadata guide](https://www.manageengine.com/products/service-desk/sdpop-v3-api/changes/change.html#meta-info-for-change-add) publishes `metainfo.fields` objects. Both current published Change metadata examples passed the existing normalizer during this review. The locally retained fixed message identifies an invalid field identifier or shape, but no raw metadata was saved. Five bounded Change metadata GETs established that ten numeric keys occurred specifically inside `roles.fields`, each with a matching `id` and `type=lookup`. The parser now supports that exact role-slot shape, assigning a deterministic internal identifier rather than using free-text names. The final probe normalized 86 definitions successfully. Synthetic cases reject numeric keys in unrelated containers, modules, or mismatched IDs.

Synthetic tests demonstrate behavior and privacy boundaries. They do not prove that a particular installed system's server-side 500, timeout or permission denial is repaired. User and administrator actions are described in [coverage recovery](../guides/coverage-recovery.md).

A one-row live asset-module probe passed parsing and intentionally reached its configured one-row cap. A computer probe bounded to three attempts did not establish a successful list through the documented fallback chain; the server-side compatibility problem remains visible and needs the administrator/vendor workflow. No full live assessment or complete-instance coverage is claimed.
