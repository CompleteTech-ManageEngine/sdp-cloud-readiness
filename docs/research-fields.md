# Field discovery evidence and implementation boundaries

Reviewed against official ManageEngine documentation and the verified ServiceDesk Plus Postman publisher on **2026-10-07**. These are on-premises V3 sources; Cloud and MSP URL patterns must not be substituted. No customer server was queried during research.

## Verified mechanisms

| Module | Documented read | Required context and result | Coverage boundary |
|---|---|---|---|
| Requests, including service resources | `GET /api/v3/requests/metainfo` with `input_data={"template":{"id":"<observed template ID>"}}` | Use the current portal's ID in `PORTALID`; the template ID must come from that portal's request-template inventory. Metadata includes resource-question API names. | Template-specific metadata. Union distinct field IDs/API names across inspected templates; never count repeated layout appearances as distinct custom fields. Uninspected templates and unattached administrator fields remain a gap. |
| Changes | `GET /api/v3/changes/metainfo` | Official Postman GET, `PORTALID` header, response `metainfo.fields`; `/changes/<observed ID>/metainfo` is also documented for edit-form metadata. | Form metadata, not evidence of a complete administrator UDF registry. The record-specific variant can be used as a documented fallback with observed IDs only. |
| Assets, computers and printers (new API) | `GET /api/v3/asset_assets/_metainfo`, `/asset_computers/_metainfo`, `/asset_printers/_metainfo`, with `input_data={"for":"advanced_filter"}` | Official Postman GETs with `PORTALID`; `metainfo.fields` includes nested UDF field dictionaries and constraints. | Generic Asset metadata covers the base type. It does not enumerate every product-type-specific custom field. |
| Individual asset product types | `GET /api/v3/<documented product-type API plural name>/_metainfo` | ManageEngine's build-15100 change guide explicitly documents product-type-specific metadata; its example is `/asset_servers/_metainfo` with no template selector. Names must be discovered from the documented product-type/module catalog and validated before extending an exact GET allowlist. | Only additional fields associated with that product type's layout appear. A successful response still does not prove that all configured but unattached fields were discovered. |
| CMDB/CI types (build 15100+) | `GET /api/v3/<observed CI-type API plural name>/_metadata` | The official CMDB comparison documents this exact GET as **Get CI Type Details**; response definitions are in `metadata.metainfo.fields`. Select API names from the authenticated `ci_types` inventory and register the exact metadata path for that portal. | Type-layout scope. Configured CMDB fields must be attached to a CI type's layout; this does not certify unattached fields or uninspected types. Metadata layout, hierarchy and other configuration content are discarded. |
| Legacy assets/workstations | `GET /api/v3/assets/metainfo` or `/workstations/metainfo`, `input_data={"template":{"id":"<observed product type ID>"}}` | Official Postman GETs with `PORTALID`; results contain asset `udf_fields`, workstation `workstation_udf_fields`, and legacy `ci_*_fields` containers. | Compatibility fallback only. The new Asset API starts at SDP build 15100; the vendor's stated legacy-support period ended in April 2026, and legacy reads expose only older fields. Do not call this current comprehensive coverage. |
| Departments | `GET /api/v3/departments/_metainfo` | Official Postman GET with `PORTALID`, `metainfo.fields`. | Department schema only. This does not establish User or Technician UDF coverage. |
| Space campus/structure/floor/room | `GET /api/v3/udf_fields`, `input_data={"module":{"name":"space_campus|space_structure|space_floor|space_room"},"list_info":{"start_index":1,"row_count":100}}` | Separate documented module selectors, `PORTALID`, `udf_fields` list and `list_info.has_more_rows`. | Applicable only to the explicitly documented module. Never treat an unfiltered request, or one Space example, as the universal Request/Change/Project registry. |

## Explicit gaps in public field-definition documentation

No current, public, official generic UDF-definition list or schema route was verified for Problems, Projects, Releases, Users, Technicians, Contracts or Purchase Orders. Their documented record APIs expose UDF **values**, which are different from definitions. Do not invent `/problems/_metainfo`, `/projects/metainfo`, `/users/udf_fields`, or similar routes by analogy.

The [CMDB V1/V3 comparison](https://help.servicedeskplus.com/cmdb-api-v1-and-v3-comparison) provides a supported field route through **type-specific `_metadata`**, even though a generic `/cis/_metainfo` was not verified. The executable field strategy uses that documented route and its distinct nested response wrapper. CI types without a validated observed `api_plural_name` remain explicit gaps; a display name or arbitrary response URL is not substituted.

The legacy Asset metainfo reference explicitly names `/api/v3/product_types` as a source of product-type IDs. The field engine also accepts product-type IDs actually observed on collected legacy asset/workstation records; it does not need to assume a product-type list response wrapper. IDs from a modern `/asset_modules` record must not automatically be interpreted as IDs for the older template selector. Workstation metadata uses types observed on computer records, not every product type in a general catalog.

For these modules the scanner can retain **observed UDF API names only** from already-collected rows/details, without copying the associated values into metadata or reports. Mark this as inferred, partial schema evidence. Do not assert the field's display name, configured type, default, length, mandatory flag or allowed-value set from a value or naming convention. Maintain a separate metadata coverage result per portal/module so a missing Request definition read does not become a universal permission diagnosis.

## Normalization rules

1. Parse only a verified `metainfo.fields` mapping, or the documented `udf_fields` definition-list wrapper. Missing/malformed wrappers are parse/compatibility gaps, never an empty successful registry.
2. UDF containers are identified by explicit `type: "udf"` or a documented UDF container (`udf_fields`, `user_udf_fields`, `workstation_udf_fields`). Preserve the full field path so the same internal ID in two containers does not collide.
3. Retain internal ID/API name, display label, type/display type, `constraints.max_length`, mandatory/read-only flags, portal ID, module, source endpoint, template/product-type context, and evidence level. Missing flags stay unknown, not false.
4. Retain option counts, maximum option length, unsupported-option-character counts, default character lengths, and numeric-default digit counts when definitions expose them. Do not retain option labels, defaults, field descriptions, scripts, lookup values or response `href` links. Never follow arbitrary links embedded in metadata.
5. Treat fields inside a documented UDF container as additional fields. Whether each was originally vendor-provided or locally created may remain unknown, particularly converted CMDB attributes; do not infer customer ownership from `udf_` alone.
6. Deduplicate the same metadata field across templates by stable internal ID/API path within the same portal and module. Retain all observed template/product-type associations. Do not merge unrelated portal fields merely because IDs or labels match.
7. A module metadata failure is an operation-specific diagnostic. A 403 cannot prove a module is disabled, an API key is invalid, or an additional role is required.
8. If constraints differ between inspected forms, retain each constraint/context variant, report ambiguous type/mandatory/read-only flags as unknown, and retain the greatest length actually observed as an exposure indicator. Do not assert that this maximum is allowed on every template.

## Implemented collection behavior

`FieldDiscovery` shares the environment's client and global budgets. Each generator step issues at most one logical `get_json` call; any transport retry uses the same global pacing and attempt allowance. Module work can be interleaved with other portals and bounded detail samples. `refresh_observed_keys()` incorporates additional UDF names found in later samples without issuing requests.

Requests use only observed incident/service template IDs. Change metadata can fall back to the documented record-specific form only with an observed Change ID. Current assets inspect validated type-specific paths from the asset catalog. CMDB uses observed `ci_types[].api_plural_name` with the documented `_metadata` suffix. Both register the exact metadata path for that portal only; missing/invalid API names remain coverage gaps. Older asset/workstation strategies inspect every selected observed product-type selector as a separate target. A successful fallback on one type does not complete other types.

An actual custom asset product type with an API name in the documented `custom_asset_...` family is discoverable through `/asset_modules`; its fields can be inspected. An actual custom CI type with an observed `cmdb_...` API name is discoverable through `/ci_types`; its layout fields can be inspected. These capabilities do not establish a universal custom-module registry. No public official on-premises GET that enumerates every arbitrary Custom Module was verified in this review. The Cloud Postman operation that reads a user-supplied custom-module API name belongs to a different product/authentication model and is not an on-premises discovery fallback.

An explicit source result of `MODULE_NOT_ENABLED`, `MODULE_NOT_AVAILABLE`, or `PORTAL_NOT_ACCESSIBLE` skips further metadata probes for that module and retains the original diagnostic. A denied record list does not itself prove a separate metadata operation will be denied. Only documented compatibility failures trigger compatibility fallbacks; permission failures do not cause a chain of alternative probes.

The default metadata limit is 20 observed form/type targets per module. Zero means no separate target cap, still subject to global request and time budgets. A capped template/type inventory is partial. Budgets and interruption retain definitions and completed metadata targets already observed; a target that never obtained an HTTP attempt remains unscanned with an unknown count.

`form_scope_complete` means all enumerated, selected form scopes were inspected and the relevant source catalog was complete. It is different from `registry_complete`. Form metadata leaves `registry_complete` false because fields not attached to a form may be absent. A successfully exhausted, documented Space-module `udf_fields` list can establish its additional-field registry coverage. Space strategies are dormant unless that exact module is actually observed; the scanner does not assume that every portal has Space Management.

## Build compatibility and migration implications

[Official on-premises release notes](https://www.manageengine.com/products/service-desk/on-premises/readme-new.html) document important shape changes: build 14900 changes Request pick/radio values to objects, multiselect/checkbox values to object lists, and resource-field handling; build 15100 separates asset product types from CMDB CI types; build 15200 replaces Request Life Cycle with Request Workflow. Normalizers must support observed versions without querying undocumented version endpoints.

Later documented field-name changes remove type indicators from generated UDF names, and custom-module/custom-association fields may lack the `udf_` prefix entirely. Some custom-module and CI-relationship payloads no longer use `udf_fields`/`cm_fields` holders. Absence of a familiar prefix/container cannot establish absence of customization. This is another reason observed-key fallback must remain incomplete and must not infer data types.

The [migration limitations](https://help.servicedeskplus.com/migration-limitations) document field-count limits, field-option character changes, oversized defaults/values, type conversions, Problem administration exclusions, common-user-field duplication, incident/service name collisions and Asset radio-field restrictions. Apply a constraint only to the documented module/type. A source definition that permits longer text than Cloud is **potential exposure inferred from metadata**, not proof that existing values exceed the target limit. An observed value exceeding a known limit is separate confirmed source evidence. Field/form-rule case-insensitive-name restrictions must not automatically be claimed for every UDF name.

Do not infer that a missing or incomplete metadata response means zero custom fields. Do not apply a 250-Request-field or 50-User-field limit to CMDB/Asset/other modules without a directly supporting Cloud reference and target-edition/context qualification. Additional-field inventory and associated template coverage must be visible beside all resulting migration findings.
